# Sprint 2 experiment: loading GeoTIFFs

**Question:** Where should the TIFF be read, and with which library, so that the
Training tool can (1) show the image, (2) list its bands and size, and (3) return
the *exact original* band values of a clicked pixel?

**Test image:** synthetic 4-band (Red, Green, Blue, NIR) uint16 GeoTIFF in UTM 15N
(EPSG:32615), 10 m pixels, deflate compressed — the same structure as Sentinel-2 / Landsat
surface reflectance. Generated by `sample_data/make_sample_tiff.py`. The top-left
16×16 block stores `row*100 + col` in the Blue band so a wrong pixel is caught immediately.

Reproduce: `python experiments/tiff_loading_experiment.py` then
`cd experiments/js && npm install && npm start`.

## Results (best of 3 runs, one Linux machine; your laptop will differ)

| Image | File | rasterio: read all bands | rasterio: screen preview PNG | rasterio: one-pixel lookup | tifffile: read all | geotiff.js (browser-side): read all | Pillow |
|---|---|---|---|---|---|---|---|
| 512 × 384 | 1.1 MB | 7 ms | 25 ms | 2.6 ms | 8 ms | 70 ms | ❌ cannot open |
| 2048 × 1536 | 18 MB | 76 ms | 382 ms | 2.7 ms | 120 ms | 565 ms | ❌ cannot open |
| 4096 × 4096 | 97 MB | 428 ms | 797 ms* | 2.8 ms | 697 ms | 2 917 ms (~600 MB RAM) | ❌ cannot open |

\* preview downsampled to 2048 px on the longest side.

All three working readers returned the correct pixel (`pixel_check = true`) and found the CRS.
Pillow raised `UnidentifiedImageError` on every file: ordinary image libraries cannot read
4-band 16-bit satellite TIFFs.

## What we learned

1. **Pillow / ordinary image viewers are out.** They cannot read multi-band 16-bit TIFFs.
2. **rasterio was the best server-side reader.** It was the fastest library tested. It reads the CRS
   and the pixel↔map transform, and it can read a single pixel without loading the
   whole image (2.7 ms whatever the image size). It is also the library the Model / Learning & Tools
   group will use in Python, so all groups get the same numbers.
3. **tifffile works but is lower level.** It gives raw GeoKeys only and returns bands as the
   *last* axis (rows, cols, bands), while rasterio uses (bands, rows, cols). Mixing the two would
   cause band-order bugs, so we will use rasterio everywhere.
4. **Reading the TIFF in the browser (geotiff.js) costs too much.** It was 4–7× slower and kept the whole image in
   browser memory (~600 MB for 4096²). The file has to reach the server for training anyway.
5. **Large images need a downsampled preview.** A full-resolution PNG of a 4096² image was 34 MB
   and took 2.4 s. Capping the preview at 2048 px brought it to 0.8 s / 9 MB. Click → pixel lookup
   always reads the *original* file, so labels are exact even when the display is downsampled.
   For very large scenes we will add map tiles in a later sprint.

## Decision

The backend reads the TIFF (Python + rasterio) and sends the browser **a display PNG** plus
**exact pixel values on request**. The browser only draws and handles clicks. See
`docs/platform_decision.md`.
